## Findings, ranked by severity

### F1 — P1: expired parked missions can make valid due reveals exceed the gas budget

**Location:** `contracts/src/core/Missions.sol:349–357`, especially the loop at line 351. The simulator mirrors the scan in `packages/rules/src/sim/missions.ts`.

`_checkOrder` scans the entire parked list. Expired order windows and expired forfeit graces do not remove entries from that list. Missions leave only through reveal, recall, or forfeit.

The outgoing cap bounds parked missions by **20 × the number of players**, not by 20 globally. Multiple accounts are allowed. A sufficiently large parked list is therefore reachable, including after a keeper outage or a concentrated arrival backlog.

**Trigger:** many old hidden missions remain parked; their arrivals are more than 60 seconds old. A new, valid hidden mission becomes due. There is no pending-queue backlog, and none of the old missions can logically block its reveal, but its reveal still reads every old parked entry.

**Measured evidence:** a temporary Solidity harness seeded parked missions with arrivals 120 seconds in the past, distributed ownership within the per-player mission cap, and added one fresh valid mission. Storage was marked cold before calling the real `Game.reveal` path. The pending heap was empty.

| Expired parked entries | Gas measured for the reveal |
| --- | ---: |
| 1,000 | 4,056,528 |
| 2,000 | 8,003,528 |
| 4,000 | 15,902,528 |
| 8,000 | 31,700,528 |
| 10,000 | A call with 32,000,000 gas failed with empty revert data |

These are harness measurements of the scan in a constructed state, not an end-to-end benchmark of creating all those missions. The 32M budget is the budget documented by this repository; the current network limit was not independently rechecked during this review.

**Impact:** valid due reveals can exhaust the transaction gas budget even when no mission is within its ordering window. Honest missions can reach their forfeit deadline while old entries are being cleared.

This is recoverable through permissionless forfeits. It is not an irreversible contract deadlock. However, neither the 15-second ordering deadline nor the 60-second grace automatically bounds the scan or clears the state.

**Proposed fix:** maintain an ordered parked index and check the immediate predecessor of the mission being revealed. Due hidden missions are parked chronologically, and a successful reveal drain parks the mission itself. Predecessor/successor pointers can support append, removal, and order checking without scanning unrelated entries. If the predecessor's window expired, all earlier windows expired too. Mirror the structure and transitions in the simulator.

### F2 — P1, conditional on upgrading an existing proxy: inserting `lastReturn` changes the building storage layout

**Location:** `contracts/src/core/GameStorage.sol:97`.

Before the change, `owner`, coordinates, `lastUpdate`, and `centipoints` filled the first storage slot exactly. Inserting a five-byte `lastReturn` before `centipoints` pushes `centipoints` and subsequent fields into different positions.

**Trigger:** populate buildings using the implementation from `ad6289c`, then upgrade that same proxy to this implementation without migrating its storage.

**Measured evidence:** a temporary harness wrote a building through the old struct layout and read it through the current `getBuilding`. An old `centipoints` value of 600 appeared as `lastReturn = 600`; the new points read as 7 from old room-level data, and the original troop value was no longer read correctly.

**Impact:** existing building state is misinterpreted after an upgrade. This finding does not apply to a fresh deployment with empty storage, and the review did not establish that a populated production proxy currently exists.

**Proposed fix:** append `lastReturn` after the existing struct fields, or use a separate mapping. Add an upgrade compatibility test that populates the old implementation, upgrades, and verifies buildings and queues.

### F3 — P2: the two 15-second values still allow a defender to evade interception

**Location:** `docs/spec/data/game_config.yaml:115–116`; cooldown enforcement in `contracts/src/core/Missions.sol:333–336` and its simulator counterpart.

This is an interaction between the specified rules and their configuration, rather than a TS/Solidity mismatch.

**Reproduced sequence:**

1. A defender's recalled fleet returns at time `R`, setting `lastReturn = R`.
2. A garbage hidden mission arrives at `R+1` and remains parked. It can belong to a cooperating account and need not target the defender.
3. The interception attack arrives at `R+2`.
4. The attacker attempts to reveal at `R+10`. It fails `OutOfOrder`, because the garbage mission's window ends at `R+16`.
5. At `R+15`, the defender sends the returned troops away. The cooldown has expired, and the attack remains hidden and parked.
6. At `R+16`, the attacker reveals successfully. The attack resolves against an empty building.

A simulator reproduction used public send/recall transitions for the returning fleet, a one-troop garbage mission, and a valid attack. Twenty defender troops escaped at `R+15`.

**Impact:** even an online attacker attempting to reveal promptly cannot preserve the interception in this state. The ordering rule forces its reveal beyond the return cooldown.

**Proposed fix:** size the return cooldown above:

```text
hidden order window
+ supported gap between return and attack arrival
+ inclusion / processing margin
```

For the documented approximately three-second gap, a 15-second cooldown cannot cover a 15-second ordering hold. A larger value should be chosen together with an explicit latency budget and a regression test for this sequence.

### F4 — P2: backlog retries put advances after the reveal that prevents them executing

**Locations:** `apps/web/src/state/game.tsx:350` and `:421`; related automatic-arrival path at `:395–403`.

`revealPlan` first processes an unlimited number of due missions on a clone. It can therefore select a reveal that would fail the real four-mission drain with `Backlog`.

The action retry path constructs its prefix as:

```text
[reveals, advances, action]
```

Because reveals now drain, the first reveal can revert before any of those advances executes.

**Reproduced sequence:**

1. Thirteen hidden missions are due and remain queued.
2. Their order windows have expired, but their 60-second reveal graces have not.
3. The client knows a valid plaintext for a due mission and includes its reveal before an unrelated action.
4. The initial attempt and all three ordinary retries fail in that first reveal. No prefixed advance is reached.
5. The fallback performs eight separate `advance(1)` operations, leaving five due missions.
6. The final reveal still fails `Backlog`, and the action fails.

Replaying the same initial state with three `advance(4)` calls **before** the reveal and action succeeds.

**Impact:** the normal retry mechanism cannot catch up the queue as intended. The unlimited simulation hides the execution precondition from the plan.

**Proposed fix:** place advances before reveals and plan against the same execution order. Route automatic arrival reveals through backlog handling too. That effect currently records its attempt before submission and does not retry automatically after a failed attempt; it relies on a later action or the keeper.

The last behavior partly predates the diff, but adding the drain to reveal introduces the relevant backlog failure into that path.

### F5 — P3: documentation retains contradictory statements

**Locations:**

- `docs/spec/blockchain.md:564`: garbage “harms nobody but its sender,” although the new order rule deliberately lets it delay other reveals.
- `docs/deploy-arbitrum.md:135`: “the bond is lost,” although there is no bond.
- `docs/spec/blockchain.md:601` and `docs/deploy-arbitrum.md:113`: reveal cost descriptions mention drain work but omit growth with the parked-list scan.

**Trigger:** follow the documentation when reasoning about garbage behavior, outage recovery, or reveal gas.

**Proposed fix:** remove the bond remnant, describe the bounded ordering delay accurately, and update cost claims after bounding the scan. Some cited sentences predate this diff; they are included because the requested review explicitly covered stale documentation.

## Checks that did not produce additional findings

### Simulator and contract exactness

The reviewed implementations match in these areas:

- Reveal checks: drain, existence/hidden/returning, grace, commitment hash, target, cover, cargo, order, and requeue.
- Cooldown checks immediately after `settleForAction` for public and hidden sends.
- `lastReturn` updates only when returning troops are credited to an origin still owned by the mission owner.
- Station arrivals do not update `lastReturn`.
- Original `(arrival, seq)` comparison, self-exclusion through `seq >=`, original-arrival window, and parked-list-only inspection.

“Every due hidden mission ahead is parked after the drain” is true **after a successful drain**. At that point no due mission remains queued. If the drain hits `Backlog`, the transaction rolls back and does not execute the order check. The rollback does not create an ordering bypass.

### Other defender actions

No additional action was found that preserves returned troops while extracting or shielding them during the cooldown:

- Abandoning destroys the building's troops.
- Account transfer preserves the player identity and the building's cooldown state.
- Family leadership handover does not transfer troops or buildings.
- A vacation started after the attack was sent does not protect against that attack.
- Recall acts on an outgoing mission rather than troops already home.
- Cancellation actions do not extract troops already home.
- A new station send from the resting building is subject to the send cooldown.

### Keeper

The new hold propagation and live/expired partition match the order rule. `Backlog` and `OutOfOrder` remain retryable rather than being classified as garbage.

For a fixed due hidden mission, every qualifying blocker expires by that mission's original arrival plus 15 seconds. Later arrivals cannot keep extending its ordering hold. This leaves 45 seconds before forfeiture, assuming gas, queue progress, and keeper latency permit the reveal.

The keeper's end-of-tick head check uses its original queue snapshot. A reveal starting from a parked-only state can therefore wait until the next tick for processing. That behavior predates this diff; the mission is already revealed and cannot then be forfeited as hidden.

### Client projection and ordering

The arrival sorting and simulated rejection of held-back plaintexts agree with the rule. The park/reveal/process projection was not found to introduce an additional state-machine mismatch. The concrete client execution problem found is F4: planning assumes more queue progress than the submitted prefix provides.

## Coverage gaps

Counting expected errors across all 34 generated differential scenarios produced:

| Error | Recorded occurrences |
| --- | ---: |
| `TroopsResting` | 0 |
| `OutOfOrder` | 0 |

The random generators mostly jump by hours or days. Hidden-arrival sampling is not enough to exercise the two 15-second boundaries meaningfully. `allHome` / `_allHome` deliberately skip the cooldown for scripted flows; that is useful for those flows but does not provide negative coverage.

Add targeted generation branches and assertions requiring both errors to occur. Also add these regression cases:

- Cooldown after recalled and forfeited missions return.
- No cooldown update when the origin was abandoned; a replacement building at that coordinate must not inherit the return.
- Successful station arrivals do not start cooldown.
- A second return resets the cooldown boundary.
- Revealing through a backlog rolls back parking and gives `Backlog` before later reveal errors.
- A future mission can be revealed while an older mission is parked; ordering is checked only for due reveals.
- F3's interception sequence.
- F4's backlog prefix and fallback sequence.
- Large expired parked lists and upgrade compatibility, if upgrades are supported.

Same-second arrival ordering is already covered by the added unit tests and is not being claimed as missing.

## Design verdict

The two rules are reasonable ways to retain queue progress while limiting reveal reordering and protecting returned troops. The current **15/15 pairing does not cover the stated interception guarantee**, because ordering can force an honest reveal beyond the cooldown.

Fifteen seconds for ordering is a plausible nominal budget with the unchanged 10-second round margin, but it still needs latency measurements that include decrypt work, keeper tick scheduling, inclusion, and burst processing. The return cooldown needs additional room for the supported arrival gap and that latency budget.

The proposed direction is to keep both rules, fix their timing relationship, and replace the global scan with an ordered parked index. No equally simple single rule was identified that provides both non-stalling behavior and the same interception protection under the accepted constraints.
